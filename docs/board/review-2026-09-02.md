# Board Review: Configurable Tab Strip Positions

## Summary

The feature has clear user value, a compatible settings contract, and a defensible launch-time architecture. It introduces no new network, identity, personal-data, dependency, or privilege surface. Broad release was conditioned on accessible sidebar resizing and stronger evidence across the four-position interaction matrix.

## Decision

**Recommendation:** CONDITIONAL APPROVE

**Conditions:**

1. Make the vertical resize handle keyboard and automation accessible.
2. Clear resize state on pointer capture loss/cancellation and reject non-primary presses.
3. Compile the packaged XAML/resources and exercise Top, Bottom, Left, and Right.
4. Verify titlebar, overlays, high contrast, DPI, and core tab operations in the packaged app.

## Top Risks

| # | Risk | Severity | Mitigation |
|---|------|----------|------------|
| 1 | Pointer-only resize handle | High | Focusable control, arrow-key resizing, localized automation properties |
| 2 | Four-position interaction matrix lacks full end-to-end automation | High | Packaged-app matrix plus focused model/local tests |
| 3 | Pointer capture loss leaves stale drag state | Medium | Reset on capture loss and cancellation |
| 4 | Custom TabView template can drift from upstream WinUI | Medium | Keep template self-contained and review on WinUI updates |
| 5 | Native titlebar and deferred overlays can regress in non-top layouts | Medium | Build and packaged-app verification |

## Security Review

The attack surface is limited to an existing local settings JSON enum and existing tab-drag paths. STRIDE categories are pass or not applicable; the feature adds no authorization, cryptography, network, secret, IPC, or privileged operation. No security weakness warrants a CWE assignment, and no dedicated security audit is required beyond normal repository gates.

## Legal and Compliance

There is no new privacy, vendor, contract, export, or data-retention concern. Accessibility parity is the material compliance consideration; the resize handle must be usable without a pointer and must expose meaningful automation text.

## Executive Review

### Business Value Assessment

- **Stated Value:** Better workspace customization for wide displays, many tabs, and vertical workflows.
- **Gaps:** Adoption and satisfaction baselines are not yet available.
- **Success Metrics:** Product correctness is measurable; customer-outcome metrics should follow release telemetry and feedback.
- **Strategic Alignment:** Aligned with Terminal customization and developer productivity.
- **Business Value Verdict:** Promising

### Executive Readiness

- **Overall:** Needs Work
- **Strengths:** Clear scope, compatible default, bounded architecture, no recurring service cost.
- **Concerns:** Accessibility and packaged-app interaction evidence.
- **Funding Blockers:** None after release-hardening conditions are met.

### Recommendation

Fund and complete release hardening. Keep the relaunch boundary; further investment in live switching or persisted sidebar width should be driven by demonstrated adoption rather than speculation.

## Resolution

The implementation now includes keyboard and automation support for the resize handle, primary-button gating, capture-loss/cancellation handling, and complete enum/default deserialization coverage. Remaining visual and native-window conditions are tracked in the test plan.
